# Совместимость протоколов 2PChat

Реализовано для основного Android-клиента с Go-ядром и Python reference.
Номер приложения, handshake, encrypted packet, групповой suite и версия
прикладной совместимости — независимые величины.

## Текущая матрица

| Уровень | Значение | Политика |
| --- | --- | --- |
| Прикладное согласование | current=1, minimum=1 | Первая реализованная версия декларации |
| Pairwise handshake | 3 | Существующий подписанный transcript без изменений |
| Double Ratchet packet | 4 | Существующие ключи, KDF и AAD без изменений |
| Клиент без декларации | legacy, версия неизвестна | Базовый личный чат; дополнительные групповые функции отключены |
| Будущий клиент | Например current=4, minimum=1 | Версия 1 и пересечение известных возможностей |
| Непересекающиеся диапазоны | Например [1,1] и [2,4] | Отказ при получении аутентифицированной декларации |

Числа 2/3 для capabilities из исходного задания не были реализованными
историческими версиями. Они не приписываются выпущенным клиентам.
Поддержка старого клиента здесь означает совместимый handshake v3 и базовый
pairwise wire format. Возврат к отвергнутым криптографическим форматам, в том
числе handshake v2 в Go, не добавляется.

## Обмен и аутентификация

После существующего X3DH-bootstrap клиент отправляет обычный `identity_info`
в зашифрованном Double Ratchet канале с дополнительным полем:

```json
{
  "type": "identity_info",
  "fingerprint": "<authenticated X25519 fingerprint>",
  "protocol": {
    "protocol_version": 1,
    "min_supported_version": 1,
    "capabilities": ["pairwise_double_ratchet_v1", "pairwise_x3dh_v1"]
  }
}
```

Старые клиенты уже понимают `identity_info` и игнорируют новое поле. Старая
подпись handshake остаётся проверяемой. Декларация защищена AEAD существующей
сессии; отдельная подпись Ed25519 для неё не заявляется. Внешняя сеть не может
переписать или вырезать поле из аутентифицированного ciphertext.

Android bridge объявляет capabilities автоматически, даже без nickname.
Standalone Go Manager сохраняет прежний автоматический обмен при заданном
nickname; явный профиль в `NewManager(..., profile)` также включает его.
Низкоуровневые Go/Python `Session` не добавляют неожиданных прикладных сообщений:
пользователь API отправляет `identity_info` через reliable API; декларация
подставляется сессионным слоем. Python discovery bridge уже выполняет этот обмен.

Состояния соединения:

1. **Pending:** декларация ещё не получена. При minimum=1 доступен базовый чат,
   но не групповые расширения. Молчание не считается доказательством старой версии.
2. **Legacy:** получен аутентифицированный `identity_info` без поля `protocol`.
   UI предлагает обновление; версия неизвестна (`protocol_version=0` в snapshot).
3. **Negotiated:** проверены диапазоны и обязательные pairwise capabilities.
4. **Closed:** некорректная декларация, несовместимость, изменение декларации
   внутри сессии или обычное отключение. Capabilities больше не действуют.

После переподключения согласование выполняется заново. Декларации не сохраняются
в SQLCipher, preferences или backup как полномочия контакта. Повторная идентичная
декларация допустима; порядок capabilities незначим. Изменение capabilities или
диапазона требует новой сессии. Неизвестные дополнительные поля игнорируются.
При поднятом minimum>1 нельзя использовать отсутствие декларации для отправки
или получения прикладных данных, включая бинарные кадры.

## Реестр и ограничения

Реестр и алгоритм Android находятся в
`2pchatGO/android/core-go/pkg/protocol`; Python реализует тот же контракт в
`messenger/core/capabilities.py`. Kotlin читает результат из Go, не согласовывает
версии самостоятельно и не доверяет результату, присланному peer.

| Capability | Go standalone / Python | Android Go bridge |
| --- | --- | --- |
| `pairwise_x3dh_v1` | Да, обязательна | Да, обязательна |
| `pairwise_double_ratchet_v1` | Да, обязательна | Да, обязательна |
| `group_suite_v1` | Нет | Да: существующие group frames v1 и suite-v1 |
| `group_suite_v2` | Нет | Да: существующий suite-v2 |
| `group_tombstones_v1` | Нет | Да: текущие авторизованные tombstone placeholders |
| `group_succession_v1` | Нет | Да: сертификат, heartbeat, revocation, claim |

Не заявляются вымышленные `group_tombstones_v2` или гарантии удаления данных
на чужом устройстве. Discovery и настройка Tor предшествуют этой сессии и не
переключаются на менее строгую политику по её capabilities. Предыдущее Android
дерево с Python сохраняет базовую совместимость; его групповой runtime не
включён в новый Android Go профиль.

Версии — целые числа 1..65535, minimum <= current. Декларация ограничена 8192
байтами, список — 64 строками, идентификатор — 64 ASCII-символами.
Имена соответствуют `[a-z][a-z0-9_]*_v[1-9][0-9]*`. Дубликаты capabilities,
повторные значимые JSON-поля, null вместо декларации, дробные версии и
неполные декларации отвергаются. Неизвестные корректные capability names
игнорируются при пересечении, но не превращаются в разрешённые функции.

`negotiatedVersion = min(local.current, remote.current)` должен быть не меньше
обоих minimum. Активны только известные обеим сторонам capabilities, допустимые
для выбранной версии. X3DH и Double Ratchet обязательны для текущей базовой сессии.

## Группы и деградация функций

Проверки работают в Kotlin перед отправкой и в Go непосредственно на границе
отправки, в том числе после восстановления очереди на новом соединении.
Приём в Go и групповой роутер Kotlin также проверяют capabilities.
`group_sync_batch_v1` проверяется вместе с вложенными событиями; key packages
учитывают поле `suite`. Неизвестные `group_*` не отображаются как текст чата.

При отсутствии возможности операция не отправляется; существующая очередь
может повторить её после подключения совместимого клиента. Нельзя сообщать
об успешной операции только на основании постановки её в очередь.
Базовый личный чат остаётся доступен. До установления соединения отправка
может инициировать обычное подключение; отсутствие snapshot не разрешает
обход финальной проверки в Go.

Suite-v2 **не** заменяется автоматически на suite-v1 для одного получателя:
это изменило бы подписанные события, эпоху и семантику группы. Текущая группа
suite-v1 продолжает использовать suite-v1 с объявившими её клиентами.
Новый сертификат succession разрешён только когда все участвующие удалённые
члены группы имеют активные сессии с соответствующей capability. Отсутствие
связи означает отсутствие подтверждения поддержки. Уже существующие
сертификаты не удаляются при временном отключении участника.

## Границы безопасности и обзор реализации

- Атакующий контролирует сеть и входящие JSON, может быть аутентифицированным
  злонамеренным peer. Доверие к ключу по-прежнему определяется текущим TOFU/pin
  и проверкой fingerprint, а не декларацией capabilities.
- Peer может лгать о своей реализации. Capabilities разрешают выбор wire
  behavior, но не доказывают выполнение ACL, удаление данных или честность peer.
- Удаление целого зашифрованного кадра или прекращение обмена остаётся DoS:
  состояние может остаться Pending, дополнительные функции не включатся.
  Это не основание отключать аутентификацию или выбирать слабую криптографию.
- Нет обещания защиты от отката ПО самим владельцем устройства между сессиями:
  постоянный запрет старых версий по истории контакта намеренно не вводится.
- Новый mutex защищает snapshot в Go; наружу возвращается копия. Результат
  принадлежит конкретной `Session`; новая сессия не наследует его от старой.
  Существующая синхронизация ratchet и порядок ACK не заменены.
- JNI `nativeGetPeerProtocol` читает текущую сессию по fingerprint. Входная
  Java-строка копируется и освобождается на том же вызове; временная C-строка
  освобождается после создания Java-строки. Новых native handles, callbacks,
  Java global refs и потоков не добавлено; mutex не удерживается при callback.
- Wire signatures, KDF, AEAD, nonce/counters, ACL, persistence и сетевые политики
  сохраняют прежнюю семантику. Проверки capabilities не заменяют их проверок.

## Правила последующих релизов

1. Сохранять базовый pairwise формат, пока он безопасен. Отделять несовместимость
   криптографии от отсутствия необязательной функции.
2. Добавлять новую capability для нового wire behavior; не переопределять
   существующее имя. Объявлять её только после реализации и тестирования.
3. Аддитивная функция сама по себе не требует повышения minimum. Для breaking
   change документировать новую версию, допустимые capabilities и миграцию.
4. Перед повышением minimum публиковать матрицу отказов и период предупреждения
   в release notes. Не удалять поддержку по формуле N+3 без анализа действующих
   клиентов. Срочное прекращение небезопасного протокола описывать отдельно.
5. Для новой операции обновить финальные send/receive gates, Kotlin requirements,
   snapshot/UI при необходимости и тесты. Для групп проверять весь набор
   затронутых участников до изменения общей политики/эпохи.
6. Проверять same/older/future/no-overlap/legacy, malformed input, переподключение,
   скрытие неизвестных control frames и межъязыковой чат/файлы.

## Проверки

Из `2pchatGO/android/core-go`: `go test ./...`, `go test -race ./...`, `go vet ./...`.
Для настоящего Go↔Python interop задать `P2PCHAT_PYTHON_ROOT` в корень репозитория
и поставить `.venv/Scripts` первым в PATH: тесты `TestPythonGoSessionChatAndFileEnvelopeInterop`
и `TestPythonGoNegotiatedSessionInterop` иначе пропускаются.

Из корня: установить `messenger/requirements.txt`, затем `.venv/Scripts/python.exe -m pytest`.
Из Android: `gradlew.bat test lint assembleDebug`. Фокусный Kotlin-набор:
`com.example.twopchat.protocol.ProtocolCompatibilityTest`.
Device/UI/E2E со старым APK и новым APK требует подключённых устройств и
не заменяется host-тестами либо успешной сборкой.
