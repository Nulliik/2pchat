## 1. Общий обзор и философия системы

**2PChat** — это бессерверный (Serverless), строго приватный Peer-to-Peer мессенджер, созданный для обеспечения максимальной конфиденциальности общения без использования центральных серверов пересылки сообщений или хранения пользовательских данных.

### Ключевые архитектурные принципы:
- **Zero-Trust & Zero-Server:** Отсутствует единая точка отказа или сервер, собирающий логи, метаданные или историю переписки. Все данные хранятся исключительно на конечных устройствах участников.
- **P2P Direct Connectivity:** Устройства связываются напрямую через локальную сеть (LAN) или оверлейную IPv6-сеть (Yggdrasil Network), дополняемую механизмом NAT Traversal.
- **Cryptographic Sovereignty:** Каждое устройство самостоятельно генерирует свои асимметричные ключи идентификации. Доверие строится на криптографических отпечатках (Fingerprints).
- **Offline-First Resilience:** Система поддерживает остойчивость к временным обрывам связи. Сообщения накапливаются в локальной очереди (Durable Outbox) и автоматически доставляются при появлении узла в сети.

## 2. Обнаружение собеседника и сетевой транспорт (Peer Discovery & Transport)

Для установления прямого P2P-соединения между собеседниками 2PChat использует гибридную многоуровневую систему обнаружения и маршрутизации.

```text
[ Устройство А ]                                             [ Устройство Б ]
       │                                                            │
       ├──── 1. Local Multicast (mDNS / UDP Broadcast) ─────────────┤ (Локальная сеть LAN)
       │                                                            │
       ├──── 2. Yggdrasil Mesh (IPv6 Overlay Network) ──────────────┤ (Глобальный P2P)
       │                                                            │
       └──── 3. STUN / UPnP / Rendezvous Tracker ───────────────────┘ (Прямой проброс NAT)
```

### 2.1. Локальное обнаружение (LAN / mDNS)
- **Механизм:** Использование протокола mDNS (Multicast DNS) и целевых UDP Broadcast-пакетов на локальном сетевом интерфейсе.
- **Принцип работы:** Устройства периодически анонсируют сервис `_2pchat._tcp.local.`, содержащий имя пользователя, порт слушающего сокета и криптографический отпечаток.
- **Результат:** В пределах одной Wi-Fi или проводной сети собеседники обнаруживают друг друга за **50–200 миллисекунд** без использования интернета.

### 2.2. Глобальная P2P-сеть Yggdrasil (IPv6 Overlay Mesh)
- **Механизм:** Интеграция с криптографической оверлейной сетью **Yggdrasil**.
- **Принцип работы:** Каждое устройство получает уникальный IPv6-адрес из подсети `200::/7`, математически привязанный к его криптографическому публичному ключу.
- **Маршрутизация:** Сообщения маршрутизируются через глобальный P2P-граф узлов Yggdrasil. Это позволяет двум узлам находить друг друга из любой точки мира, даже если оба находятся за строгим NAT (Symmetric NAT) или мобильными операторами.

### 2.3. Rendezvous & Tracker Infrastructure
- **HTTP / UDP Trackers:** Для быстрого сопоставления текущих IP-адресов контактов 2PChat использует распределённые легкие трекеры без сохранения сообщений. Узлы отправляют обновлённый хэш своего эндпоинта.
- **UPnP & NAT Traversal:** Автоматическое открытие портов на роутерах через UPnP (Universal Plug and Play) и определение внешних IP-адресов/портов с помощью STUN-запросов.

## 3. Криптография и сквозное шифрование (End-to-End Encryption)

Криптографический стек 2PChat спроектирован на базе современных стойких алгоритмов с высокой скоростью работы на мобильных устройствах.

### 3.1. Ключи идентификации и отпечатки (Identity Keys & Fingerprints)
- **Алгоритм подписи:** **Ed25519** (Edwards-curve Digital Signature Algorithm).
- **Формирование идентичности:** При первом запуске создаётся уникальная пара ключей `(Ed25519 Private Key, Ed25519 Public Key)`.
- **Криптографический отпечаток (Fingerprint):** Вычисляется как SHA-256 хэш от публічного ключа Ed25519 и кодируется в 64-символьную шестнадцатеричную строку (HEX).
- **Сравнение отпечатков (Out-of-Band Verification):** Собеседники могут визуально или через QR-код сравнить свои отпечатки. После подтверждения контакт получает статус **`VERIFIED` (Доверенный)**, исключая атак «человек посередине» (MITM).

### 3.2. Протокол Double Ratchet (Двойной Храповик)
Для каждого тет-а-тет диалога устанавливается сессия по протоколу **Double Ratchet** (аналог Signal Protocol).

```text
               ┌──────────────────────────┐
               │    Master Key / Root     │
               └────────────┬─────────────┘
                            │
              DH-Ratchet (X25519 Exchange)
                            │
               ┌────────────▼─────────────┐
               │        Chain Key         │
               └────────────┬─────────────┘
                            │
          Symmetric-Ratchet (HKDF-SHA256)
                            │
               ┌────────────▼─────────────┐
               │       Message Key        │ ──► AES-256-GCM / ChaCha20
               └──────────────────────────┘
```

#### Протокол состоит из двух храповиков:
1. **Diffie-Hellman (DH) Ratchet (Асимметричный храповик):**
   - Использует эфемерные ключи **X25519**.
   - При каждом смене направления общения (ответе собеседника) генерируется новая пара эфемерных ключей X25519 и выполняется вычисление общего секрета DH.
   - Обеспечивает **Post-Compromise Security (PCS)**: если злоумышленник компрометирует ключи в текущий момент времени, первый же новый ответ собеседника полностью восстановит защиту для будущих сообщений.

2. **Symmetric KDF Ratchet (Симметричный храповик):**
   - На базе функций **HKDF-SHA256** (HMAC-based Extract-and-Expand Key Derivation Function).
   - Из ключа цепочки (Chain Key) шаг за шагом генерируются одноразовые ключи сообщений (Message Keys).
   - Ключ сообщения уничтожается в оперативной памяти сразу после шифрования/расшифрования.
   - Обеспечивает **Perfect Forward Secrecy (PFS)**: даже при компрометации устройства прошлые сообщения не могут быть расшифрованы, так как одноразовые ключи не сохраняются.

### 3.3. Шифрование сообщений (Message Payload Encryption)
- **Симметричный шифр:** **AES-256-GCM** (Galois/Counter Mode) или **ChaCha20-Poly1305**.
- **Nonce/IV:** Для каждого сообщения генерируется уникальный 96-битный случайный вектор инициализации (Cryptographic Nonce).
- **Аутентифицированные данные (AEAD):** В вектор аутентификации включаются ID отправителя, ID получателя и порядковый номер сообщения, защищая от подмены метаданных.

## 4. Протокол передачи и приёма сообщений (Wire Protocol & Messaging)

### 4.1. Формат кадра (Bounded JSON Wire v1)
Все сетевые пакеты упаковываются в строго валидируемые JSON-кадры с ограниченным размером:

```json
{
  "v": 1,
  "id": "msg_9f8b2c1a-...",
  "sender": "Alice",
  "recipient": "Bob",
  "type": "chat_message",
  "payload": "BASE64_ENCRYPTED_PAYLOAD",
  "dh_pub": "BASE64_X25519_EPHEMERAL_KEY",
  "seq": 42,
  "timestamp": 1785981200000,
  "signature": "BASE64_ED25519_SIGNATURE"
}
```

### 4.2. Гарантия доставки и обработка оффлайна (Durable Outbox)
1. **Durable Outbox (Очередь исходящих):** Сообщение атомарно сохраняется в локальной шифрованной БД со статусом `PENDING`.
2. **Экспоненциальный Backoff (Retry Strategy):** При отсутствии связи или ACK-ответа повторные попытки отправки выполняются со снижающейся частотой (1s, 2s, 4s, 8s, 16s... до 1 часа).
3. **Delivery ACKs & Read Receipts:**
   - **Delivery ACK:** При получении пакета получатель автоматически отправляет подтверждение доставки.
   - **Read Receipt:** При просмотре чата открытым экраном генерируется квитанция прочтения (`READ`), и отправляется входящему узлу.

### 4.3. Управление уведомлениями Android (Notification Engine)
- **Интеграция с Android System:** Сообщения используют `NotificationCompat.MessagingStyle` с отображением аватарок собеседников и возможностью прямого ответа из шторки (RemoteInput).
- **Динамическое угасание уведомлений (Auto-Cancel & Suppression):**
  - Если чат с собеседником **открыт на экране**, вызов системных звуков и вывод плашек в шторку автоматически **блокируются**.
  - При входе в чат или при отправке сообщения существующие плашки этого собеседника **моментально удаляются из шторки** Android.

## 5. Архитектура и протокол групповых чатов (Group Chat Protocol)

Групповой режим 2PChat работает по специализированному протоколу **`2pchat-epoch-aes256gcm-ed25519-v1`**, спроектированному для бессерверных P2P-групп.

### 5.1. Модель Эпоховых Ключей (Membership Epoch Keys)
Шифрование групповых сообщений строится на понятии **Эпохи членства (Epoch)**.

```text
 [ Эпоха E=1 ] ──► (Участник C удалён) ──► [ Эпоха E=2 (Новый epoch_secret) ]
   Участники: A, B, C                         Участники: A, B
   Ключ: Secret_1                              Ключ: Secret_2 (рассылается A и B по P2P)
```

1. **Ключ эпохи (`epoch_secret`):** Для каждой эпохи генерируется криптографически стойкий случайный 256-битный ключ.
2. **Ротация ключей при изменении состава:**
   - При добавлении нового участника или удалении (бане) существующего владелец группы увеличивает счетчик эпохи (`epoch = E+1`) и создаёт **новый `epoch_secret`**.
   - Новый ключ шифруется индивидуально для каждого оставшегося участника и отправляется через личные защищённые Double Ratchet-сессии.
   - **Результат:** Новый участник не может прочесть историю до своего вступления, а удалённый участник не может расшифровать будущие сообщения.

### 5.2. Децентрализованный журнал событий (Replicated Event Log & HLC)
Групповой чат представляет собой реплицируемый append-only журнал событий.
- **Гибридные логические часы (Hybrid Logical Clocks, HLC):** Используются для строгого причинно-следственного упорядочивания событий от разных участников без применения централизованного сервера времени.
- **Типы событий журнала:**
  - `TEXT_MESSAGE` / `MEDIA_MESSAGE` — текстовые сообщения и вложения;
  - `MEMBER_ADDED` / `MEMBER_REMOVED` / `MEMBER_BANNED` — управление составом;
  - `ROLE_CHANGED` / `OWNER_TRANSFERRED` — изменение прав и передача владения;
  - `GROUP_INFO_CHANGED` — изменение названия, описания или аватарки группы.

### 5.3. Синхронизация Anti-Entropy & WorkManager
- **Автоматическое выравнивание:** Если участник был оффлайн и пропустил несколько эпох или сообщений, при выходе в сеть запускается процесс **Anti-Entropy Sync**.
- **Сверка хешей:** Узел сравнивает свой крайний хеш состояния (`control_head`) с владельцем группы или активными участниками и автоматически дозапрашивает недостающие события и ключи прошедших эпох.

### 5.4. Система ролей и управление доступом (ACL Policy)
- **Иерархия ролей:**
  1. **`OWNER` (Владелец):** Обладает абсолютными правами, управляет передачей владения, назначает администраторов. В любой момент времени в группе строго **ровно один Owner**.
  2. **`ADMINISTRATOR` (Администратор):** Назначает модераторов, меняет настройки группы, удаляет участников.
  3. **`MODERATOR` (Модератор):** Удаляет сообщения пользователей, ограничивает право писать (`RESTRICTED`).
  4. **`MEMBER` (Участник):** Стандартные права на чтение, отправку сообщений и медиа.
  5. **`RESTRICTED` / `BANNED` / `LEFT`:** Ограниченные, заблокированные или вышедшие участники.

## 6. Безопасность хранения данных и метаданных

### 6.1. Шифрование базы данных (SQLCipher)
- Все локальные данные (история сообщений, списки контактов, ключи эпох, служебные логи) хранятся в базе данных, зашифрованной с помощью **SQLCipher**.
- **Шифр:** **AES-256-CBC** с производным ключом через **PBKDF2 HMAC-SHA512** (64 000 итераций).
- Ключ расшифровки БД хранится в аппаратном хранилище ключей устройства (**Android Keystore System** / EncryptedSharedPreferences).

### 6.2. Шифрование файлов и медиавложений
- Файлы разбиваются на блоки фиксированного размера.
- Каждый блок шифруется симметричным ключом AES-GCM.
- Метаданные файла содержат адресацию по содержимому (Content-Addressed Storage, **CID**) на базе SHA-256 хэша.

### 6.3. Защита от утечек метаданных
- Имена пользователей и аватарки передаются только внутри шифрованных каналов.
- Индикаторы набора текста (Typing presence) передаются зашифрованными управляющими кадрами и автоматически сбрасываются по таймауту (6 секунд).

### 📌 Заключение
Архитектура **2PChat** объединяет криптографическую стойкость Signal Protocol (Double Ratchet), автономность P2P-сетей (Yggdrasil & mDNS) и остойчивость реплицируемых журналов событий для групповых чатов. Это гарантирует абсолютную независимость пользователя от сторонних серверов и полную безопасность переписки.
