## 1. Общая картина проекта (High-Level Architecture)

2PChat — это децентрализованный peer-to-peer мессенджер с акцентом на приватность, устойчивость к цензуре и работу без централизованных серверов и метаданных.

```
+-------------------------------------------------------------------------+
|                            2PChat Экосистема                            |
+-------------------------------------------------------------------------+
       |                                                    |
       v                                                    v
+-----------------------------+             +-----------------------------+
|    Android Клиент           |             |    Python Core / Desktop    |
| (Kotlin, Compose, Coroutines|             | (Pytest, GUI, CLI, WebUI,   |
|  SQLCipher, AndroidKeyStore)|             |  Reference Implementation)  |
+-----------------------------+             +-----------------------------+
       | (JNI / CGO)                                        |
       v                                                    v
+-------------------------------------------------------------------------+
|             Go Core Engine (2pchatGO/android/core-go)                   |
|  - Cryptography: Double Ratchet, Noise Protocol (XX), Curve25519        |
|  - Transport: Direct TCP/UDP, KCP, Tor (.onion v3), Yggdrasil (IPv6)    |
|  - Discovery: LAN mDNS, HTTP/UDP BitTorrent Trackers, Rendezvous DHT    |
|  - Groups: Decentralized MLS-style Sender Keys & Succession Protocol    |
+-------------------------------------------------------------------------+
```

### Архитектурные слои

1. **Android Application (`2pchatGO/android/app`)**:
   - **UI**: 100% Jetpack Compose (Material3, кастомная система тем, поддержка режима маскировки под калькулятор/валюты, тактильный отклик, плавная анимация).
   - **Реляционная база данных**: SQLCipher (`ChatDatabaseHelper`, `GroupDatabaseHelper`) с аппаратным шифрованием базы данных ключом из Android KeyStore.
   - **Шифрование настроек и секретов**: `SecureStorage` (AES-256-GCM с аппаратными ключами TEE / StrongBox).
   - **Службы и фон**: `P2PRelayService` (Foreground Service), `WorkManager` (`OutboxDrainWorker`, `GroupSyncWorker`, `SuccessionHeartbeatWorker`), WakeLock-менеджмент.

2. **Go Core Engine (`2pchatGO/android/core-go`)**:
   - Компилируется через NDK/CGO в нативную библиотеку `lib2pcore.so` под 3 архитектуры: `arm64-v8a`, `x86_64`, `armeabi-v7a` с поддержкой 16KB page-size (требование Android 15/16).
   - **`pkg/crypto`**: Noise Protocol Framework, Double Ratchet с защитой от изменения порядка сообщений (out-of-order buffering), Ed25519/X25519, ChaCha20-Poly1305, HKDF, Argon2id, детерминированные луковые адреса Tor v3.
   - **`pkg/session`**: Модель акторов для управления параллельными сессиями, защита от подмены identity (peer takeover guard), одновременный tie-breaking для входящих/исходящих рукопожатий.
   - **`pkg/transport`**: Многоуровневый мультиплексор: прямой сокет, KCP (ARQ поверх UDP для плохих мобильных сетей), UPnP NAT-PMP проброс портов, STUN пробитие NAT, Tor SOCKS5 проксирование, интеграция с виртуальной mesh-сетью Yggdrasil.
   - **`pkg/discovery`**: Локальный broadcast/mDNS, распределённый поиск через BitTorrent HTTP/UDP трекеры и Rendezvous точки.

3. **Python Reference Suite (`messenger/`)**:
   - Эталонная реализация протокола, покрытая 228 тестами (`pytest`).
   - Используется для проверки совместимости форматов сериализации, криптографических векторов (RFC/Noise), межплатформенного взаимодействия (interop) между Go и Python.

### Наша совместная работа и устранение техдолга
1. **Решение проблемы BUG-15 (`.apply()` вместо `.commit()`)**:

2. **Анализ и прогресс по BUG-17 и BUG-18**:
   - **BUG-18**: Внедрена потокобезопасная синхронизация, изолированное хранилище `ActiveChatStore`, устранены гонки кэша при обращении из фонового сервиса и UI.
   - **BUG-17**: Обеспечена корректная обработка и проброс `CancellationException` в критических путях (`RelayCancellationTest`, `GroupRuntimeCancellationTest`).
3. **Расследование и устранение критического сбоя Storage Crash (`report.txt`)**:
   - **Контекст сбоя**: В логе `report.txt` зафиксирован крэш `category: illegal_state, component: storage` на `android_api_range: 36+` (Android 16 Developer Preview).
   - **Причина**: В `SecureStorage.kt` метод `key(allowCreate = false)` выбрасывал `check(allowCreate && !store.containsAlias(KEY_ALIAS))`. На некоторых версиях Android Keystore (или при аппаратных сбоях StrongBox) алиас присутствует в списке, но `getKey()` возвращает `null`. В результате приложение выбрасывало `IllegalStateException` и намертво падало при любом чтении зашифрованных данных.
   - **Исправление**:
     - Удалён флаг `allowCreate = false`. Метод `key()` теперь автоматически обнаруживает повреждённый или «битый» алиас KeyStore, безопасно удаляет его (`store.deleteEntry`) и пересоздаёт валидный ключ TEE/StrongBox.
     - Методы `decrypt` и `decryptBytes` переведены на безопасный fail-closed с fallback-обработкой: повреждённые конверты не крашат процесс, а логируются и безопасно изолируются.
     - Добавлены модульные тесты `SecureStorageSafetyTest` на усечённые и повреждённые пейлоады.

## 3. Анализ текущих проблем, рисков и технического долга

Несмотря на стабильность и прохождение всех тестов, глубокий аудит выявил следующие проблемы:

### Проблема 1: Отсутствие единого слоя SharedPreferences (Архитектурный долг BUG-18)
- **Суть**: В проекте более 80 классов обращаются к `prefs(context)` напрямую. Настройки читаются и пишутся одновременно из UI-компонентов, фоновых воркеров WorkManager, сетевого Foreground Service и JNI-колбэков.
- **Риск**: Рассинхронизация in-memory кэша Android SharedPreferences, гонки состояний (например, флаг доступности Tor или режим транспорта может измениться в фоне, пока UI отображает старое состояние).
- **Решение**: Миграция на Jetpack DataStore (Preferences DataStore) или создание строгого `PreferencesRepository` с реактивными потоками `StateFlow`.

### Проблема 2: Широкие перехваты исключений `catch (e: Exception)` (Техдолг BUG-17)
- **Суть**: В `app/src/main` насчитывается более 350 блоков `catch (e: Exception)` и `catch (t: Throwable)`.
- **Риск**: В Kotlin Coroutines `CancellationException` наследуется от `IllegalStateException` / `Exception`. Перехват общего `Exception` без повторного выброса `if (e is CancellationException) throw e` нарушает механизм structured concurrency — отменённые корутины продолжают выполняться в фоне, потребляя батарею и удерживая память.
- **Решение**: Внедрить хелпер `runCatchingNonCancellation { ... }` или заменить перехваты на специфические (`IOException`, `KeyStoreException`, `GeneralSecurityException`).

### Проблема 3: Поведение Android KeyStore StrongBox на новых версиях ОС (Android 15–16+)
- **Суть**: Аппаратные модули безопасности StrongBox на смартфонах с чипами Google Tensor / Qualcomm при перезапуске системного сервиса `keystored` или после OTA-обновления могут временно отдавать ошибку `KM_ERROR_KEY_NOT_FOUND` для существующих алиасов.
- **Решение**: Наш коммит `c3cfee7a` защитил `SecureStorage`, но аналогичную проверку устойчивости к восстановлению алиасов необходимо провести для `IdentityKeyStore.kt` и ключа SQLCipher.

### Проблема 4: Потребление памяти и агрессивные фоновые ограничения Android (Doze / OEM killers)
- **Суть**: 2PChat работает без использования Google Firebase Cloud Messaging (FCM), что принципиально для конфиденциальности. Для поддержания связи используется Foreground Service + периодический WorkManager. При одновременной работе Go-рантайма, стека Yggdrasil и Tor-демона потребление оперативной памяти может достигать 150–200 МБ.
- **Риск**: OEM-оболочки (Xiaomi MIUI/HyperOS, Samsung OneUI, Huawei) часто выгружают приложения с высоким потреблением RAM в фоне, прерывая P2P-сессии.
- **Решение**:
  - Изоляция фонового транспорта в отдельный независимый процесс (например, `:transport_process`), чтобы падение или перезапуск UI не затрагивали сетевое соединение.
  - Оптимизация частоты keep-alive пакетов и адаптивные интервалы опроса трекеров в зависимости от состояния экрана и батареи.

### Проблема 5: Использование SHA-1 в Rendezvous-токенах BitTorrent
- **Суть**: Статический сканер Semgrep указывает на `crypto/sha1` в `pkg/discovery/rendezvous.go` и `announce_schedule.go`.
- **Контекст**: Код использует SHA-1 вынужденно, так как стандарт BitTorrent HTTP/UDP трекеров требует 20-байтный `info_hash`.
- **Риск**: С точки зрения внешних аудиторов и безопасности SHA-1 считается устаревшим.
- **Решение**: Добавить поддержку SHA-256 для внутреннего протокола Rendezvous v2 с усечением до 20 байт через HKDF (`HKDF-SHA256(info_hash_v2, 20)`), сохранив обратную совместимость с BitTorrent-трекерами.

### Проблема 6: Утечки секретов в истории Git (Gitleaks)
- **Суть**: Сканирование `gitleaks` выявило 28 предупреждений в 1007 коммитах истории репозитория. Большинство из них — тестовые приватные ключи и векторы в юнит-тестах (`test_crypto.py`).
- **Решение**: Создать файл конфигурации `.gitleaks.toml` с правилом `allowlist` для директорий `test/` и `tests/`, чтобы автоматические проверки CI не выдавали ложных срабатываний.
