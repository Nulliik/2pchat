## 1. Общая картина проекта (High-Level Architecture)

2PChat — это децентрализованная, peer-to-peer платформа обмена сообщениями, спроектированная по принципу **Zero-Trust** и **Zero-Metadata**. В системе отсутствуют центральные серверы авторизации, базы данных учётных записей или провайдеры push-уведомлений (Google FCM).

### Ключевые криптографические и протокольные инварианты
1. **Noise_XX_25519_ChaChaPoly_BLAKE2s**:
   - Взаимная аутентификация пиров без раскрытия публичных ключей внешнему наблюдателю.
   - Трёхшаговое рукопожатие: `-> e`, `<- e, ee, s, es`, `-> s, se`.
2. **Double Ratchet**:
   - Смена эфемерных DH-ключей на каждом цикле ответа (DH Ratchet).
   - Симметричные KDF-цепочки отправки и приёма (Symmetric-key Ratchet) для защиты от раскрытия будущих и прошлых ключей при компрометации отдельного сообщения.
   - Буферизация до 1000 пропущенных ключей сообщений для сохранения доставки при потере пакетов.
3. **Групповой протокол (MLS-подобный Sender Keys + Event Sourcing)**:
   - Полная децентрализация: отсутствие сервера группы.
   - Ротация эпохальных ключей через Signed Group Events.
   - Автоматический протокол преемственности (Succession Protocol): если создатель группы выходит или офлайн, детерминированный консенсус передаёт владение следующему активному администратору без раскола (Split-Brain Guard).
4. **Многоуровневый стек транспорта (Cascade Routing)**:
   - Приоритет 1: Прямой LAN / WAN сокет (минимальная задержка).
   - Приоритет 2: Виртуальная ячеистая сеть Yggdrasil (IPv6 криптографический mesh `200::/7`).
   - Приоритет 3: Луковая сеть Tor v3 (максимальная анонимность, обход любых блокировок и NAT).

## 3. Детальный аудит проблем, уязвимостей и технического долга

В ходе аудита всей кодовой базы выделены 4 основные категории проблем:

### Категория A. Архитектура настроек и конкурентность (BUG-18)
* **Текущее состояние**: Прямые вызовы `prefs(context)` разбросаны более чем по 80 классам (`MainActivity`, `P2PRelayService`, `TorManager`, `GroupChatCoordinator`, `ChatDatabaseHelper`).
* **В чём проблема**: SharedPreferences в Android загружает XML в память один раз на процесс. Если запись происходит асинхронно из фонового воркера или Foreground Service, а чтение — из UI-потока, возможен кэш-дрейф (cache drift).
* **Риск**: Гонка состояний при переключении сетевых тумблеров (например, флаг режима Tor или Yggdrasil может обновиться в фоне, а UI-экран продолжит отображать старое состояние).

### Категория B. Обработка ошибок и корутины (BUG-17)
* **Текущее состояние**: В кодовой базе Android-клиента насчитывается свыше 350 блоков `catch (e: Exception)` и `catch (t: Throwable)`.
* **В чём проблема**: В Kotlin Coroutines исключение отмены `CancellationException` является подтипом `IllegalStateException` / `Exception`. Если корутина отменяется родителем (например, пользователь закрыл экран чата или остановил службу), а внутри блока `try` стоит широкий `catch (e: Exception)`, исключение проглатывается.
* **Риск**: Нарушение структурированного параллелизма (Structured Concurrency). Дочерние задачи продолжают выполняться «вхолостую», удерживая соединения, память и разряжая батарею.

### Категория C. Мобильные ограничения ОС и энергопотребление
* **Текущее состояние**: 2PChat содержит внутри одного APK:
  1. Kotlin/Java среду выполнения.
  2. Встроенный демон Tor (`libtor.so`).
  3. Go-рантайм ядра (`lib2pcore.so`).
  4. Стек виртуальной сети Yggdrasil.
* **В чём проблема**: Суммарное потребление оперативной памяти может достигать 150–220 МБ.
* **Риск**: Системный механизм Android LMK (Low Memory Killer) и агрессивные OEM-оптимизаторы батареи (MIUI, ColorOS, Samsung OneUI) закрывают фоновый сервис при блокировке экрана. Пир уходит в офлайн, а P2P-сообщения задерживаются до ручного открытия приложения пользователем.

### Категория D. Сетевой уровень и криптографическая гигиена
1. **BitTorrent Rendezvous и SHA-1**:
   - В `pkg/discovery/rendezvous.go` вычисляется SHA-1 для rendezvous-точек. Это обусловлено 20-байтным ограничением BitTorrent `info_hash`. Хотя энтропия обеспечивается секретным словом пиров, в долгосрочной перспективе внешние регуляторы и аудиторы требуют отказа от SHA-1.
2. **Время жизни секретов в JVM Heap**:
   - Пароли и токены в ряде мест преобразуются в `java.lang.String`. Объекты `String` в Java неизменяемы (immutable), и их невозможно безопасно занулить (`zeroize`) до тех пор, пока их не соберёт Garbage Collector.
3. **Срабатывания Gitleaks**:
   - В истории git зафиксировано 28 предупреждений (в основном тестовые векторы и заглушки ключей в `test_crypto.py`). Требуется официальный `.gitleaks.toml` с белым списком тестовых файлов для чистоты CI-пайплайна.

## 4. Дорожная карта и конкретные пути решения

### Этап 1: Немедленные улучшения (1–2 недели)
1. **Централизация настроек (Решение BUG-18)**:
   - Создать фасад `PreferencesRepository` (на базе Kotlin `StateFlow`), инкапсулирующий все чтения и записи настроек. Полностью изолировать прямой доступ к `prefs(context)`.
2. **Безопасные корутины (Решение BUG-17)**:
   - Внедрить extension-функцию `runCatchingNonCancellation { ... }`:
     ```kotlin
     inline fun <R> runCatchingNonCancellation(block: () -> R): Result<R> {
         return try {
             Result.success(block())
         } catch (e: CancellationException) {
             throw e
         } catch (e: Throwable) {
             Result.failure(e)
         }
     }
     ```
   - Заменить широкие перехваты в горячих путях передачи сообщений и фоновых службах.
3. **CI Security Gate**:
   - Добавить `.gitleaks.toml` с правилами исключения тестовых директорий, чтобы автоматический аудит безопасности возвращал чистый `PASS`.

### Этап 2: Повышение живучести в фоне и безопасность (1–2 месяца)
1. **Оптимизация фонового режима (Battery & Doze Resilience)**:
   - Перевести периодические проверки сети с таймеров на системные колбэки `ConnectivityManager.NetworkCallback`.
   - Внедрить адаптивный интервал Keep-Alive: 30 секунд при активном экране, 5–10 минут при заблокированном экране и питании от батареи.
2. **Интерактивная верификация контактов (Anti-MitM)**:
   - Реализовать в UI генерацию и сканирование QR-кодов отпечатков ключей (Safety Numbers / SAS), позволяя пользователям подтверждать подлинность собеседника при личной встрече.
3. **Память и зануление секретов**:
   - Исключить использование `String` для приватных ключей и паролей БД; перевести весь внутренний конвейер на `ByteArray` и `CharArray` с обязательным вызовом `SecurityUtils.zeroize()` в блоках `finally`.

### Этап 3: Архитектурные инновации (3–6 месяцев)
1. **Двухпроцессная архитектура (`:core` process isolation)**:
   - Вынести Tor и Go-рантайм в отдельный изолированный фоновый сервис-процесс (`com.example.twopchat:core`).
   - Преимущество: падения или утечки памяти UI-слоя не обрывают активные соединения, а UI-процесс освобождает память при сворачивании.
2. **Постквантовая криптография (PQXDH)**:
   - Модернизировать рукопожатие ядра Go: объединить классический Diffie-Hellman на Curve25519 с постквантовым алгоритмом инкапсуляции ключей **ML-KEM-768 (Kyber)**. Это обеспечит защиту переписки от атак класса «Store Now, Decrypt Later».
3. **Модернизация Rendezvous v2**:
   - Ввести протокол Rendezvous v2 на базе `HKDF-SHA256` с сохранением обратной совместимости для v1.
